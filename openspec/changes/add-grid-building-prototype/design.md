# Design

## Context

目标为当前仓库中的新建网页应用。已检查仓库结构、OpenSpec 配置及能力清单，目前没有应用源代码、测试、包管理配置或已有能力规范。动机见 `proposal.md`，行为合同见本变更的三份 `specs/*/spec.md`。

用户已确定正俯视方格地图以及 React + PixiJS。运行环境以桌面浏览器和鼠标为主，状态仅保存在当前页面内；无需对接后端或迁移历史数据。

本设计满足新外部依赖、新数据模型及跨界面和渲染模块协作的条件，因此创建完整设计文档。

## Goals / Non-Goals

**Goals:**

- 网格规则拥有唯一的建筑和占地事实来源，画面与 DOM 控件都从同一份状态派生。
- 摆放交互与施工生命周期独立，使取消草稿不会影响已开工建筑，完工也不会打断摆放。
- 将坐标转换、占地校验与确认提交隔离为可独立验证的边界。
- 明确 React 挂载、PixiJS 异步初始化及销毁的所有权，保证开发模式和页面尺寸变化下的稳定行为。

**Non-Goals:**

- 本设计不建立通用 ECS、物理系统或可插拔渲染框架。
- 不设计联网同步、持久化格式、资源交易或复杂模拟时间系统。
- 不引入相机拖动或玩家控制的缩放；适配视口只做自动等比缩放。

## Decisions

### 1. Vite + TypeScript + React，直接集成 PixiJS

使用 Vite 的 React TypeScript 基础，PixiJS 采用 v8 API，由单个场景适配器直接管理 Application、Container、Graphics、Text 和 ticker。具体兼容版本及锁文件在实现阶段固定。

React 负责页面布局、建筑列表、操作提示和 DOM 确认按钮；PixiJS 负责地图与游戏画面。相较于为每格建立 DOM 节点，该分工更适合后续增加精灵和效果。原生 Canvas 2D 已在探索中比较，用户选择 PixiJS；Phaser 的场景与游戏设施不属于当前需求。

暂不增加 `@pixi/react`：当前只有一个画布，直接管理其生命周期即可，额外的场景协调层会增加依赖和所有权边界。后续可在场景复杂度增加时重新评估。

### 2. 领域状态为唯一事实来源

按职责划分领域规则、交互控制器、PixiJS 场景适配器和 React 界面。领域层不导入 React、PixiJS 或浏览器坐标 API。

核心数据包括：

| 数据 | 内容 |
| --- | --- |
| 建筑定义 | 类型标识、名称、占地宽高、施工时长、视觉样式标识 |
| 地图 | 列数、行数、每格逻辑尺寸、逐格的建筑实例标识或空值 |
| 建筑实例 | 唯一标识、类型、网格锚点、开工时刻、施工时长、施工或完成状态 |
| 摆放状态 | 未选择、预览或待确认；当前类型、预览锚点、鼠标是否位于地图；待确认时保存候选标识与固定锚点 |

采用按行存储的格子占用数组，索引为行号乘列数加列号。矩形占地从定义和锚点推导，校验返回有效结果或越界、重叠原因。占用数组和建筑实例只允许通过领域命令同步修改。

交互控制器承接选择、地图移动、固定候选、确认、取消、Esc 和施工更新。React 通过订阅稳定的界面状态快照更新列表与控件，PixiJS 使用相同状态更新场景。鼠标像素坐标和逐帧动画不驱动 React 页面重绘；吸附格变化和离散交互才更新相关状态。

选择轻量控制器而不是额外状态库，原因是只有单局地图和一套摆放流程。避免 React 与 PixiJS 各自维护一份建筑列表，防止取消后残留建筑或画面与占用不一致。

### 3. 显式摆放状态机与候选身份

| 当前状态 | 输入 | 结果 |
| --- | --- | --- |
| 未选择 | 选择建筑 | 进入对应类型预览 |
| 预览 | 地图鼠标移动 | 更新吸附锚点与有效性 |
| 预览 | 点击有效地图位置 | 保存唯一候选标识及固定锚点，进入待确认 |
| 预览 | 点击无效位置 | 保持预览并反馈原因 |
| 待确认 | 鼠标移动或地图点击 | 保持固定候选 |
| 待确认 | × 或 Esc | 保留类型及原锚点，恢复预览 |
| 待确认 | 有效 ✓ | 提交建造，消费候选，恢复同类型预览 |
| 待确认 | 无效 ✓ | 保持候选并显示原因，不修改建筑和占用 |
| 预览或待确认 | 选择另一类型 | 丢弃原草稿，进入新类型预览 |
| 预览 | Esc | 清除选择并退出摆放 |

一个候选只能被消费一次。确认命令携带候选身份；已消费、已取消或已被切换取代的旧候选确认请求直接忽略。该规则保证快速双击和旧回调不会重复建造。

取消保留原候选网格锚点，不把按钮的屏幕坐标转成地图坐标。鼠标仍在控件上时暂不显示跟随幽灵，下一次有效地图指针事件才继续跟随。待确认建筑与普通幽灵使用不同显示模式，候选不随指针进出而消失。

首版默认确认后继续摆放同种建筑；切换另一类型即撤销尚未确认的草稿。这些是为完成首版交互而选定的默认规则，评审时可调整。

### 4. 所有地图定位共用一条坐标转换链

地图默认使用 24 列、18 行、每格 32 个逻辑像素。场景根容器根据地图视口自动等比适配并居中，缩放上限为 1；始终保持格子为正方形。右侧列表默认约 280 CSS 像素。

指针先转换到地图根容器的局部坐标，再分别除以格子尺寸向下取整。先检查局部坐标位于地图矩形内，再计算锚点，防止右下外边界、居中留白或负坐标被吸附回地图。

PixiJS renderer 的分辨率使用设备像素比并启用对应显示尺寸处理；逻辑坐标不能再次乘设备像素比。窗口变化通过 ResizeObserver 更新 renderer、根容器变换和控件投影，不改变网格锚点或建筑占用。

相较于直接以浏览器鼠标坐标除格子大小，共用局部坐标链能处理画布偏移、自动缩放及高密度显示。

### 5. 图层与 DOM 控件分工

场景按地图底色和网格、已建建筑、施工效果、候选与幽灵反馈组织图层。网格静态绘制，建筑对象按实例创建和更新；施工进度只更新对应的进度条。首版使用程序化 Graphics 图形和少量文字区分建筑类型与状态，不依赖外部美术下载。

React 确认控件位于画布容器的 DOM 覆盖层。将候选占地边界通过场景变换投影为 CSS 坐标，在建筑附近选择位置，并限制在地图视口内；ResizeObserver 触发重新定位。按钮具有“确认建造”“取消放置”的可访问名称。

覆盖层除控件区域外允许地图接收指针。按钮和列表事件不进入地图命令；地图输入仅接受来自地图交互面的事件。处理 pointerdown 与 click 的隔离，避免一次确认在按钮消失后落到下层地图。全局 Esc 监听随宿主生命周期注册与注销。

### 6. 确认提交与施工推进

确认命令在同一次同步状态提交内完成候选身份检查、全占地校验、建筑实例创建、全部格子占用及候选消费；校验失败不修改建筑实例和占用数组。待确认候选不提前写入占用数组，因为首版同时只能存在一个候选。

每个实例保存单调时钟的开工时刻与定义中的施工时长，进度由实际经过时间除以时长并限制到 0 至 1。使用一个共享 ticker 推进施工显示和完工转换，避免为每栋建筑创建独立定时器。页面恢复更新时按当前时间追赶进度。测试注入时钟以验证边界和并行施工。

达到施工时长时只切换实例状态和外观，不释放或重建占地。施工时钟与摆放状态机互不消费对方事件。

### 7. 资源所有权与重复初始化

React 场景宿主负责启动和销毁 PixiJS 适配器。处理异步初始化期间的卸载：已失效的初始化结果不得向页面追加画布，并应释放自身资源。清理覆盖 ticker 回调、事件订阅、ResizeObserver、DOM 监听、场景对象和 renderer。

初始化、卸载及重新挂载后，只存在一个有效画布和一组输入处理器。该约束面向 React StrictMode 与开发热更新，也纳入浏览器验证。渲染器初始化失败时在地图区域呈现可读的失败信息，避免只有空白画面。

### 8. 演示配置与验证方式

| 参数 | 首版默认值 |
| --- | --- |
| 地图 | 24 × 18 格 |
| 单格逻辑尺寸 | 32 像素 |
| 示例建筑 | 路灯 1 × 1、小屋 2 × 2、工坊 3 × 2、仓库 3 × 3 |
| 施工时长 | 各建筑默认 3 秒，定义中分别可配置 |
| 有效和无效占地 | 绿色与红色，并在无效时显示文字原因 |
| 幽灵外观 | 半透明，保持可辨认的建筑轮廓 |
| 局内状态 | 内存保存，刷新重置 |

这些数值与示例名称是设计默认值，不是用户另行确认过的产品参数；在不改变交互合同的前提下可集中调整。

使用 Vitest 验证占地、边界、重叠、状态转换、确认幂等、提交失败不留部分状态和注入时钟的施工逻辑。使用 Playwright 对真实浏览器操作进行验证，覆盖取消后重新放置、确认后立即阻挡、切换类型、Esc、按钮穿透、候选靠边时的控件及画布调整后的坐标。

浏览器验收至少检查一个常规桌面视口及高设备像素比场景，并记录能辨认幽灵、待确认、施工、完成的截图。单元测试验证确定性规则，浏览器验收验证渲染与 DOM 输入之间的协作。完成类型检查和生产构建后再交付原型。

## Risks / Trade-offs

- [DOM 控件与 PixiJS 画面使用不同坐标系] → 共用场景变换，尺寸变化后重新投影并检查高设备像素比。
- [异步初始化与 StrictMode 清理发生交错] → 为每次宿主初始化设置有效期，销毁失效实例，验收画布数量及一次输入只执行一次。
- [草稿和已开工建筑被混用] → 分离状态机，只有确认命令能同步创建实例并占地。
- [重复按钮事件造成多次开工] → 消费唯一候选身份，拒绝旧候选确认。
- [后台页面降低更新频率] → 按单调时钟的经过时间计算，恢复更新时追赶状态。
- [程序化图形的表现力有限] → 首版以占地、轮廓及状态可辨认为标准，视觉资源通过独立样式标识保留替换位置。
- [内存状态在刷新时丢失] → 按当前原型范围接受该行为，存档作为单独能力后续设计。

## Migration Plan

本项目没有既有运行版本或历史数据，无数据迁移。实现后通过类型检查、规则测试、浏览器验收和生产构建生成静态产物，再使用本地预览确认构建结果。回退时撤销此次应用新增文件及依赖，或在静态托管平台恢复上一份部署产物。
