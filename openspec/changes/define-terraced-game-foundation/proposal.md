# Proposal

## Why

当前原型验证的是正俯视矩形网格上的建筑选择、确认和施工流程，但目标游戏的核心空间规则是侧视角台阶地形：纵向代表固定高度差，建筑主要沿横向占地，地面可能为空洞，道路和上下连接会直接影响工人、牲畜和车辆的通行。若继续沿用现有的二维矩形占地假设，建筑占用、画面遮挡、道路寻路和运输线会逐步形成相互冲突的规则。

现在需要先建立一份长期项目大纲，并把台阶地形、实体地面、建筑视觉遮挡、道路类型、楼梯与斜坡、移动主体能力、工人分配和点对点运输线整理为稳定的领域契约，为后续实现和 OpenSpec 变更提供共同背景。

## What Changes

- 新增 `docs/project-overview.md`，记录游戏定位、设计支柱、坐标轴、台阶地形、建筑遮挡、道路与通行能力、工人和运输线，以及后续资源、生产、地形改造和地图生成等计划内容。
- 在 OpenSpec 项目上下文中保留一份简短的领域摘要，使后续提案能识别 `(column, level)`、实体地面、野路、楼梯、斜坡、工作地点和运输线等稳定术语。
- 建立以 `(column, level)` 为坐标的台阶世界模型；每个位置可以是实体地面或 `air`，建筑、道路和移动主体都必须依赖实体地面。
- 将普通建筑定义为单一台阶上的横向连续占地，并把逻辑占用、视觉高度和遮挡范围分开处理；跨台阶建筑作为特殊类型保留扩展点。
- 将实体地面上的默认通行方式定义为野路，并支持石板路和水泥路作为水平道路升级。
- 建立楼梯和斜坡两类高度连接：楼梯占 1 格、跨 1 个台阶且不允许车辆；斜坡占 2 或 3 个格子、跨 1 个台阶并允许车辆；多级高度差由连续结构组成。
- 明确人、牲畜和车辆在水平道路、野路攀爬、楼梯和斜坡上的通行能力与移动代价。
- 建立工人的单一主动分配模型：工人同一时间属于一个工作地点或一条运输线，并通过统一寻路执行工作或搬运任务。
- 建立单起点到单终点的运输线；系统自动计算路线，线路显示与工人实际使用的道路段、攀爬连接、楼梯和斜坡保持一致。
- 保留资源库存、生产配方、岗位容量、地形改造、道路具体数值、遮挡排序、地图生成和多站点运输作为后续大纲内容，不在本次变更中实现完整玩法。

## Capabilities

### New Capabilities

- `terraced-world`: 固定台阶高度的 `(column, level)` 世界坐标、实体地面与 `air` 格子、地面支撑和可行走性。
- `building-occlusion`: 单台阶横向建筑占地，以及独立的视觉高度、遮挡范围和跨台阶建筑扩展边界。
- `roads-and-connections`: 默认野路、石板路和水泥路，野路攀爬，以及只跨一个台阶的楼梯和 2/3 格斜坡连接。
- `agent-traversal`: 人、牲畜和车辆对水平道路、攀爬、楼梯和斜坡的通行能力与移动代价。
- `worker-assignments`: 工人对田地、工厂等工作地点或运输线的互斥主动分配和任务状态。
- `transport-lines`: 单起点到单终点的自动寻路运输线、工人分配、路线阻塞状态和可见线路。

### Modified Capabilities

无。当前仓库没有主规范能力；已有 `add-grid-building-prototype` 变更中的正俯视原型规范作为实现背景，后续实现需要逐步替换其中与台阶世界冲突的假设。

## Impact

- 需要新增项目设计文档，并补充 `openspec/config.yaml` 的简短项目上下文。
- 领域模型将从单纯的矩形占用网格扩展为地形状态、底边道路段、垂直通行结构、建筑逻辑占用与渲染遮挡分离的模型。
- 现有 `src/domain/grid.ts`、`layout.ts`、建筑类型和 PixiJS 地图适配器中的正俯视假设将成为后续实现的主要迁移点；当前变更只建立契约和实现计划，不直接修改这些代码。
- 后续实现可能影响地图坐标转换、建筑预览、占用校验、寻路、施工状态、工人状态和运输线渲染，但不需要后端、账户或联网同步。
- 测试需要从单纯的矩形放置扩展到实体地面校验、遮挡与逻辑占用分离、移动主体能力、楼梯/斜坡占地、路线一致性和阻塞重算。
