# Design

## Context

当前仓库是 React、TypeScript、Vite 和 PixiJS 的正俯视建造原型。`src/domain/grid.ts` 和 `src/domain/layout.ts` 将地图视为规则矩形格网，`GameStore` 维护矩形建筑占用，`src/ui/PixiMap.tsx` 按俯视坐标绘制地图和建筑。详见 `proposal.md` 的动机；本设计把这些原型假设迁移到侧视角台阶世界所需的长期边界。

项目尚无主规范目录，现有 OpenSpec 变更的能力规范只描述正俯视建造流程。因此本设计需要同时确定持久化项目背景、领域数据模型、寻路图和渲染适配器之间的边界。

## Goals / Non-Goals

**Goals:**

- 让地形、建筑占用、道路连接、移动能力和运输线共享确定的逻辑坐标。
- 把逻辑占用、视觉高度和遮挡排序分开，避免渲染实现反向决定游戏规则。
- 使寻路结果同时服务于工人移动和运输线显示，并能在道路变化后安全重算。
- 保留现有建造确认原型的可验证性，同时为台阶地形迁移提供分阶段路径。
- 让项目大纲成为长期领域背景，OpenSpec 规范继续承载可测试行为。

**Non-Goals:**

- 本设计不确定最终的资源种类、生产配方、经济数值或岗位具体产能。
- 本设计不实现完整的地形编辑、程序化地图生成、存档、联网同步或多人模拟。
- 本设计不规定最终美术资源、动画风格、相机缩放体验或具体遮挡特效。
- 本设计不把多站点运输、循环线路和复杂货物调度纳入首版运输线。

## Decisions

### 1. 项目大纲、OpenSpec 上下文和能力规范分层

新增 `docs/project-overview.md` 作为长期项目大纲，保存游戏定位、术语、稳定世界规则、系统关系和未来路线。`openspec/config.yaml` 只保留一段短摘要，用于让后续提案快速获得必要背景；可验证行为分别放在本变更的六个能力规范中。

选择分层而不是把完整设计塞入 `config.yaml` 或 `SKILL.md`，原因是项目大纲属于游戏领域知识，代理 skill 属于工作流程，两者生命周期和读者不同。README 继续负责运行和开发入口，不承担完整设计来源。

### 2. 以 `(column, level)` 为核心坐标，显式存储地面状态

世界使用整数 `column` 和 `level`，格子为正方形，地图配置中的横向列宽与相邻台阶高度差必须相等。地面、空洞网格与占地高亮共用方格边界，屏幕转换只使用统一的等比缩放。每个位置都可以存在，但其地面状态可以是 `air` 或实体地面；实体地面再独立声明材质、是否支撑建筑和是否可行走。台阶高度差是地图配置，而不是某个建筑或道路的属性。

概念数据关系如下：

```text
TerrainCell(column, level)
  state: air | ground
  material
  supportsBuilding
  walkable

BottomRoad(column, level)
  type: wild | stone | concrete

TraversalStructure
  kind: stairs | ramp
  footprint
  fromLevel / toLevel
  endpoints
  allowedAgents
```

选择显式 `air` 而不是只保存每列最高高度，是因为后续需要表达台阶中间的空洞、悬崖、平台和道路结构占地；选择固定 `level` 而不是任意浮点高度，则让楼梯、斜坡和寻路连接可以先限定为相邻台阶。

### 3. 将建筑逻辑占地与视觉遮挡拆成两个模型

普通建筑保存基准列、基准台阶和横向占地宽度。视觉模型另外保存高度、深度顺序和遮挡范围。建筑放置只检查实体支撑地面和逻辑占用；渲染器依据视觉模型决定绘制顺序和遮挡。

这比继续复用当前矩形 `width × height` 占用更安全，因为当前的 `height` 同时承担了格子占用和画面尺寸。桥、平台等跨台阶建筑必须声明特殊占地和支撑规则，不能由普通建筑的视觉高度隐式产生跨层碰撞。

### 4. 用底边道路段和显式高度结构生成寻路图

可行走实体地面默认拥有野路底边；石板路和水泥路替换该底边的道路类型并降低水平移动代价。道路段不直接表示垂直移动。

野路攀爬、楼梯和斜坡作为独立的高度连接。楼梯占 1 格并跨一个台阶，斜坡占连续 2 或 3 格并跨一个台阶；多级高度差由多段连接链组成。每个结构保存端点、占地、允许主体和代价，保证占地校验、寻路和渲染读取同一事实来源。

寻路层从地形、底边道路和高度结构派生节点与边：

```text
same level:  bottom road segment -> horizontal edge
level change: climb / stairs / ramp -> vertical connection edge
```

边带有主体能力约束和可配置代价。人在楼梯、斜坡和野路攀爬上可用；牲畜规则相同；车辆可使用所有水平道路和斜坡，但不可使用野路攀爬和楼梯。路线结果引用逻辑道路段和连接，而不是只保存屏幕像素。

### 5. 用主体能力配置驱动路线计算

寻路请求携带移动主体类型、起点、终点和代价配置。路线算法先过滤主体不可用的边，再比较剩余路线的总成本；无路线时返回不可达原因。使用确定性的图和代价配置，确保工人移动、运输线显示和测试结果一致。

不把能力写成道路类型的隐含分支，是为了允许未来增加其他主体或特殊道路，例如只能牲畜使用的窄路，而不重写整套寻路规则。

### 6. 工人与运输线共享任务和路线状态

工人的主动分配是一个互斥引用：`null`、一个工作地点或一条运输线。工作地点和运输线都声明岗位容量；分配变更显式释放旧岗位。暂时缺货或暂时无任务只让工人等待，不自动改派。

首版运输线只保存一个起点和一个终点。创建后自动计算路线，显示层直接绘制路线引用的道路段和高度连接。地形或道路版本发生变化时，运输线检查路线是否仍有效；失效时进入重算或阻塞，禁止工人穿过旧连接。

### 7. 领域层与 PixiJS 适配器分离

地形、建筑、道路、寻路、工人和运输线规则继续放在不依赖 React、PixiJS 或浏览器坐标的领域模块中。PixiJS 适配器负责将 `(column, level)` 和视觉体积转换为侧视画面、执行深度排序和绘制线路；React 负责目录、分配和状态控件。

地图指针输入先通过统一的侧视坐标转换得到逻辑位置，再交给领域命令。渲染缩放、设备像素比和画布偏移不得改变逻辑占用或路线结果。

### 8. 采用分阶段迁移而非直接重写当前原型

先保留现有正俯视测试作为行为基线，新增台阶领域模块和纯规则测试；随后将建筑占用、地图渲染和输入适配器逐步切换到新模型。新模型稳定后再删除或重命名当前只服务矩形网格的类型和函数。

这种迁移方式可以保留已经验证的确认、施工和订阅流程，同时把高风险的地形、遮挡和寻路变化拆成可定位的阶段。当前 PixiJS 原型不应继续扩展更多俯视专用规则。

## Risks / Trade-offs

- [逻辑层级与屏幕纵坐标方向相反，输入容易错位] → 由单一坐标转换模块负责 `level` 到屏幕位置的映射，并用边界和缩放测试覆盖。
- [斜坡占 2/3 格但内部不是普通水平道路] → 将斜坡作为带占地和端点的 `TraversalStructure`，寻路和渲染均读取其内部段，不把它拆成错误的平面道路。
- [视觉遮挡与建筑碰撞再次混用] → 建筑逻辑占地、视觉体积和遮挡范围使用独立数据，并分别测试放置和渲染结果。
- [道路改变后运输线仍引用旧路径] → 为地图通行数据维护版本或失效标记，路线变化时统一进入重算或阻塞状态。
- [当前原型的矩形网格假设扩散到 UI] → 先在领域层建立新模型，再替换 `layout.ts`、Pixi 场景和摆放预览，避免在组件中重复解释台阶规则。
- [移动代价尚未有最终数值] → 首版使用集中配置的相对代价和确定性测试，具体平衡数值作为后续调整，不改变能力边界。

## Migration Plan

1. 创建 `docs/project-overview.md`，并在 `openspec/config.yaml` 添加短领域摘要。
2. 新增独立的台阶地形、建筑占地/遮挡、道路连接和主体能力纯规则模块，先用固定样例和单元测试验证。
3. 将寻路图和路线对象接入工人分配与点对点运输线，增加路线阻塞和重算测试。
4. 更新 PixiJS 场景为侧视坐标、深度排序、建筑遮挡和道路/连接绘制；更新 React 控件以支持工作地点与运输线分配。
5. 用浏览器验收覆盖空洞地面、建筑遮挡、楼梯/斜坡车辆限制、工人重分配和线路显示；确认后再逐步移除正俯视专用实现。

回退时保留当前原型代码和测试，撤销新领域适配器及文档变更即可；不涉及持久化数据迁移或后端兼容。

## Open Questions

- 野路、石板路、水泥路、攀爬、楼梯和斜坡的具体移动代价仍需通过原型体验调平。
- 资源类型、库存容量、生产配方和运输线的货物容量将在工作地点与经济系统变更中确定。
- 地形改造是否允许把 `air` 变成实体地面，以及改造是否需要专用建筑，留给后续地图编辑设计。
